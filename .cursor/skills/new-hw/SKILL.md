# new-hw：ACM 题解是否过复杂 / 要不要优化

本 Skill 主要改**题解写法与讲解路径**，不覆盖原 `题解.md`。默认不改题面、不改测例；**唯一例外**见第 **5.5** 节：情况二的朴素/暴力在线拿满 AC 时，必须加 hack 测例（必要时同步改题面规模并上传）。

权威格式（必须先读）：

- 仓库根 `题解模板.md`
- 仓库根 `题解生成规范.md`（ACM 模式）
- 当前题目的 `题解.md`（**仅用于判定是否要改**，以及抄一二级标题 / `$变量$` / 代码围栏等**版式约定**；**不要**把「对比旧解」写进 `修改_题解.md` 正文）

出题心智（判断「能不能换成更简单算法」时）：`algorithm-contest-problemsetter`。

### 写稿原则：`修改_题解.md` 是全新题解

- **判定阶段**才读、才对照原 `题解.md`（算不算过复杂、能不能降、代码量有没有收益）。
- **落盘 `修改_题解.md` 时**：当成给新手写的**独立完整题解**，直接讲当前采用的算法与实现。
- **禁止**在 `修改_题解.md` 里出现对旧解的指涉或对比，例如：「不必使用状态压缩」「相比原题解」「不用线段树了」「旧写法是…」等。读者看不到原题解，这类句子只会突兀。
- 旧版与新版差在哪：只写在 `修改说明.txt`（给维护者看），不要写进题解正文。
- **`修改说明.txt` 句式**（一两句即可）：**原题解的解法是 $xx$，因为 $yy$（太复杂 / 对新手不友好 / …），所以新题解修改为 $zz$ 解法。** 只写解法层面的改动原因与结果，**不要**写提交过程、AC/TLE、登录失败、分数等评测流水。

## 0. 输入与产出

### 0.1 必读

| 文件 | 用途 |
|------|------|
| `<题目目录>/题解.md` | 判定对象；也是 Markdown 格式母本 |
| `<题目目录>/题面.md` | 题意、数据范围、样例；用来判断简单解能否过最大数据 |

用户 `@` 了题目目录或 `题解.md` 时，以该目录为准。缺 `题解.md` → 停止，只说缺失项。缺 `题面.md` 可继续，但必须在对话里标明「未对照数据范围」。

### 0.2 产出

- **要优化**：在**同一题目目录**写入 `修改_题解.md`，**不要**覆盖 `题解.md`。同时再写一个 `修改说明.txt`，句式为：原题解解法是…，因为…，所以新题解改为…；不要写提交/评测流水。
- **不用优化**：不写 `修改_题解.md`，也不写 `修改说明.txt`，对话里说明理由即可。

对话里先给判定（情况一 / 情况二 / 无需优化），再给文件。

## 1. 作用（按用户原话执行）

判断目前的这道题的题解是否过于复杂，就是有两种情况，这道题有更简洁，简单的解法。比如一道题可能是状态压缩dp+dfs，那可不可以直接改成dfs去做，如果有的话，这道题的题解就可以优化，第二种情况是，如果这个题确实只能用复杂解法去解，那就题解分为两部分，前半部分是讲一个暴力朴素的解法，比如暴力枚举，dfs，然后后半部分再给出正确解答，注意暴力解法也要给出c++，python，java代码，代码也要注释。然后优化题解要注意，代码要中文注释，代码书写按照简洁朴素来，因为我的题解是要给新手看的。所以总结就是这个skill就是判断当前这道题题解是否要优化，如果要优化就给一个修改_题解.md，也就是修改后的题解，注意题解格式要严格按照我原本题解的markdown格式来，包括一二级标题，变量名的markdown格式也要严格遵循。

## 2. 判定流程（先判定，再写文件）

对照 `题面.md` 的数据范围，回答四个问题：

1. **当前题解的算法核是什么？**（如状压 DP、线段树、网络流、二分答案）
2. **有没有更简洁、简单、对新手更短的正确解法？** 该解法必须**正确**，且在题面最大数据下复杂度**过得去**（不要用会 TLE/MLE 的做法冒充情况一）。
3. **优化后，讲解负担和代码量是否明显下降？** 若换解法 / 拆暴力+正解之后，三语言总代码量、核心函数行数、概念数量与原题解差不多，则**视为无实质收益 → 无需优化**。
4. **现有题解写得像不像给新手看的？** 缺中文注释、快读/花活语法、一整段不分层，才考虑「只改写法」。

### 2.0 收益门槛（硬门槛，先过再谈情况一/二）

只有同时满足下面两条，才允许写 `修改_题解.md`：

1. **算法台阶真的降了，或新手路径真的清楚了**：例如去掉状压、去掉难懂表述；**不是**「二分 + 前缀和」这种普及向组合。**例外：** 线段树 / 树状数组见 §2.1.3，不走本条否决。
2. **代码量 / 实现负担明显变小**：……若差不多、甚至更长……**不要改**。**例外：** 线段树 / 树状数组即使总篇幅变长，仍必须前补朴素（§2.1.3）。

口诀：**换了个说法但代码还那么长 = 没必要改。**

反例（不要改）：河堤高度二分答案 + 排序前缀和——算法已够朴素；若改成「先暴力枚举高度再二分扫一遍」，正解代码量几乎不降，还多出一整段暴力，属于无效优化。

### 2.1 情况一：有更简洁、简单的解法 → 整篇换成简单解

分两类，都只交**一套**解，不要无谓地拆暴力段。

#### 2.1.1 换更简单的算法核

例如：一道题可能是状态压缩 DP+DFS，那可不可以直接改成 DFS 去做。可以的话，`修改_题解.md` **整篇只写 DFS/回溯这一种解**，像新写的题解一样开讲，正文里不要提状态压缩或「不必用某某」。

典型「可降」方向（必须同时满足：正确 + 过数据范围 + **第 2.0 节收益门槛**）：

- 状压 / 子集 DP → 回溯 / 普通 DFS / 枚举子集（实现从 bit 运算变成数组/递归，**代码与概念都明显更短**）
- 最短路板子 → 网格 BFS / 堆优化非必须时的朴素 BFS
- 复杂 DP 维 → 贪心、双指针、二分答案（有证明或题解里能讲清）

（线段树 / 树状数组**不要**放在本表里「看能不能降」——见 §2.1.3。）

#### 2.1.2 算法核已经对，只是多了没必要的优化 → 去掉优化，不换解法

若原题解的**主算法已经是本题最正确、最好懂的正解**（例如本题就该用 DP，而不是硬改成 DFS），但正文/代码里堆了新手不需要的优化（滚动数组专题化、过早的空间压缩、难懂的下标收缩写法、常数级花活等），则：

- `修改_题解.md` **仍写同一算法**；
- 删掉那些没必要的优化与绕口表述，把定义、转移、代码写直白；
- **不要**为了「显得更朴素」换成另一种更难懂或更长的解法（典型反例：地宫跳格子类题，正解就是 DP，不要前半塞 DFS）；
- 代码尽量短：少一层封装、少重复注释废话、I/O 朴素即可。

为过数据而**必须保留**的剪枝（如「只更新能赶到终点的位置」）可以留，但要用白话讲清「为什么」，不要包装成高级技巧。

**禁止**：用错误贪心「简化」；把过不了最大数据的暴力当成情况一的唯一解；为「再简单一点」把已经够短的二分/前缀和/双指针再拆一遍；在算法核已正确时硬换成另一套解法。

### 2.1.3 硬性规则：线段树 / 树状数组 → 必须前补朴素（不要多想）

只要原题解（或本题正解）用的是**线段树**或**树状数组**（Fenwick / BIT），**一律走情况二**：

- **不要**纠结「能不能换成前缀和」「代码量会不会变长」「收益门槛够不够」；
- **不要**试图只用「去优化 / 换写法」糊弄过去；
- **直接**在前面补一段朴素解（例如每次询问扫一遍、暴力改点再求和），三语言都给；后面再写线段树 / 树状数组正解。

同类默认同样处理（同样不要多想）：树链剖分、网络流、主席树、重链等明显超出机考新手的板子——一律前补朴素 + 后给正解。

### 2.2 情况二：确实只能用复杂解法 → 题解分两段

**复杂**指新手难以一次上手的板子。其中 **线段树、树状数组见第 2.1.3 节硬性规则，强制前补朴素**。其余如树剖、网络流、困难 DP 等，同样优先情况二。

**不包括**（不要硬套暴力 + 正解）：排序、前缀和、二分答案、双指针、普通 DFS/BFS、简单一维 / 二维 DP——这些直接讲正解，或按 2.1.2 去多余优化即可。

前半部分是讲一个暴力朴素的解法，比如暴力枚举，DFS；后半部分再给出正确解答。注意暴力解法也要给出 C++、Python、Java 代码，代码也要注释。

**朴素段 `## 解题思路` 的第一句**必须点明正解是什么、朴素也能拿分，句式接近：

> 这道题的正解是 $xxx$，但是我们用朴素解法 $yyy$ 也能在考试时拿到一定的分数。

然后再讲题意要点与朴素怎么搜/枚举。样例和小数据能算对；最大数据会超时（或超内存），所以后面再写正解。

暴力选「新手第一反应」：枚举、DFS/回溯、模拟，不要再套一层高级板子。

**例外（仅非 2.1.3 点名的板子）**：若正解本身已经写得够短、够清楚，只是「缺一段会超时的暴力」，而补上暴力后总篇幅暴涨、对理解正解帮助不大，可选择**不写**。**线段树 / 树状数组不适用本例外。**

### 2.3 无需优化

满足任一即可判定为无需优化（不写 `修改_题解.md` / `修改说明.txt`）：

- 当前算法已是适合数据范围的最简单正确解（含：排序 + 二分、前缀和、双指针、普通 DFS 等普及组合）；
- 已按 `题解生成规范.md` 分点写思路，三语言有实质中文注释，代码总体朴素；
- **预估优化后代码量 / 概念负担没有明显下降**（第 2.0 节）。

写法很差但算法已经最简 → 仅当「缺注释 / 快读劝退 / 一大段不分层」时，才按**原算法**重写成新手向（情况一的「只改写法」）；**不要**借机换成另一套篇幅差不多的算法，也不要硬加暴力段。

更多对照见 [examples.md](examples.md)。

## 4. 代码：新手、中文注释、ACM、简洁朴素

代码要中文注释，代码书写按照简洁朴素来，因为我的题解是要给新手看的。细则以 `题解生成规范.md` 为准，本 Skill 再收紧如下。

### 4.1 ACM 结构

- 输入输出写在主函数里，题意功能写在外部函数里（Java 为 `public class Main` 的 `main` + 静态方法）。
- 三语言：Python、Java、C++ 都要有；情况二则**暴力三份 + 正解三份**。
- 默认输入合法。
- 不要用太高级语法。

### 4.2 朴素写法（优先于「竞赛风」）

- **Python**：用 `input()` / `print()` 读入写出；不要 `sys.stdin.buffer`、不要为读入而 `import sys`。
- **Java**：用 `Scanner`；默认不用快读、不用 `StreamTokenizer`。
- **C++**：`cin` / `cout`；头文件跟原题解习惯或 `iostream` + 常用容器。不要平衡树、pbds、重模板。
- 不用 lambda 堆砌、不用三目套三目、不用宏技巧。
- 循环写清楚；变量名短而直白（`n`、`ans`、`heights`），并与题面用词一致。

### 4.2.1 文字与代码变量名必须一致（硬约束）

解题思路 / 公式里出现的名字，三语言代码里要用**同一套标识符**（大小写按语言习惯微调即可，如 Python/C++ 用 `new_dp`，Java 用 `newDp`）：

- 正文写 $dp[t][i]$、实现用两行滚动时：代码里必须出现 `dp`（上一回合），本回合用 `new_dp` / `newDp`，并在注释里写明对应 $dp[t-1]$、$dp[t]$。
- 正文写 $value[i]$ / $heights$ / $P,S$：代码参数与数组也叫 `value` / `heights` / 同等名字，不要正文 `dp`、代码却全是 `prev`/`curr`/`treasure` 对不上。
- 若实现需要改名：先改文字定义，再写代码，保证读者对得上。

正解在 $n=10^5$ 且 Java/Python 有 T 风险时，仍优先朴素 I/O；若必须加 `ios::sync_with_stdio(false)`，用一行中文注释说明原因。

### 4.3 中文注释

- 三种语言都要有实质中文注释，禁止「只有一种语言有注释」。
- 注在关键步骤：循环不变量、边界、为什么排序、二分的可行含义、DFS 的递归返回值。
- 不要「定义 n」「开始循环」这类废话注释。

### 4.4 正确性

- 情况一 / 情况二的**正解**必须与题意一致，复杂度匹配题面范围。
- 情况二的**暴力**必须能手算对样例；不要求过最大数据。
- 不要在 `修改_题解.md` 里改题意或改样例答案。
- **写完 `修改_题解.md` 后必须按第 5 节做在线提交验 AC**，不能只靠本地样例。

## 5. 在线提交验 AC（强制）

凡写出了 `修改_题解.md`，必须把题解里的 **Python / Java / C++** 代码，用本仓库 `utils/submit_code_and_get_result.py` 提交到 CodeFun2000 看结果。参数与账号以 `utils/README.md` 为准；`--base-url` 固定 `https://codefun2000.com`，`--domain-id` 默认 `system`。

### 5.1 提交什么

| 题解形态 | 必须提交 |
|----------|----------|
| 情况一（只有一套解） | 该套三语言各交一次 |
| 情况二（暴力 + 正解）已写全 | **正解**三语言各交一次必须 AC；**朴素至少交一种语言（优先 C++）**确认**未满分**——若朴素满分，走 §5.5 hack，不得跳过 |
| 情况一写成了「只剩朴素解」 | 该朴素解三语言各交一次；若 AC 率不够，再按 5.3 补正解并复测 |

从 `修改_题解.md` 抽出代码围栏，落到临时文件再提交（例如 `_tmp_newhw_py.py` / `_tmp_newhw_Main.java` / `_tmp_newhw.cpp`），Java 文件名与 `public class Main` 一致。提交完可删临时文件。

语言参数（与 README 一致）：

- Python：`--lang py.py3`
- Java：`--lang java`
- C++：`--lang cc.cc14o2`（若平台习惯其它 `cc.*`，以能编过为准）

示例：

```powershell
$env:HYDRO_API_UNAME="..."
$env:HYDRO_API_PASSWORD="..."
python utils/submit_code_and_get_result.py --base-url https://codefun2000.com --domain-id system --pid P5187 --lang py.py3 --code-file _tmp_newhw_py.py
python utils/submit_code_and_get_result.py --base-url https://codefun2000.com --domain-id system --pid P5187 --lang java --code-file _tmp_newhw_Main.java
python utils/submit_code_and_get_result.py --base-url https://codefun2000.com --domain-id system --pid P5187 --lang cc.cc14o2 --code-file _tmp_newhw.cpp
```

缺 `utils`、缺环境变量、或脚本失败：按 fail closed 列出原因；**不要**假装已 AC。

### 5.2 结果怎么分流

看评测状态（AC / WA / RE / TLE / MLE / 部分分等）和通过点数占比：

1. **代码本身写错**（WA、RE、编译错误，或样例都对不上）：改 `修改_题解.md` 里对应代码与必要说明，再重新提交，直到逻辑正确。
2. **朴素解法复杂度不够**（典型：TLE、MLE，或只过约 **50%～60%** 测试点，其余超时/超内存）：说明「只讲朴素」过不了全数据。此时必须把题解改成**前半朴素 + 后半正解**（骨架同第 3.2 节情况二）：朴素段第一句点明正解名与「朴素也能拿一定分」，并写明大数据会挂；正解段给出能 AC 的做法与三语言代码。补完后对**正解**再跑一遍三语言提交，直到 AC（或说明平台不可用）。
3. **三语言正解均 AC**：在对话里简要汇报即可；**不要**把评测过程写进 `修改说明.txt`。
4. **情况二的朴素/暴力在线拿满 AC（或通过率过高，与「只能拿部分分」叙事不符）**：测例偏弱，**必须**按第 **5.5** 节加 hack 数据后再复测，不得假装「朴素也会挂」。

约 50%～60% 是经验阈值：若通过率明显偏低且失败点是 TLE，同样按第 2 条补正解；若通过率已经很高只差常数，可优先尝试不改算法、只修 I/O/语言实现后再交，仍不够再补正解。

### 5.3 与「情况一 / 情况二」的衔接

- 判定时以为情况一「简单解能过最大数据」，但**在线提交证明过不了** → 按 5.2.2 **升级为情况二结构**重写 `修改_题解.md`（正文仍不提旧题解，只写朴素再写正解），并更新 `修改说明.txt`。
- 情况二里的**正解**提交必须 AC；暴力段允许不满分，且**不允许**在终态数据下暴力满 AC（见 5.5）。

### 5.4 上传修改题解（用户要求上传时）

用 `utils/upload_sol.py`，`--solution-file` 指向该题的 **`修改_题解.md`**（不要误传原 `题解.md`）。

**只上传还没上传过的：**

| 本地标记 | 含义 |
|----------|------|
| 题目目录存在 `修改_题解.已上传` | 已成功传到平台 → **跳过**，不要再 `upload_sol` |
| 有 `修改_题解.md` 但无此标记 | **本轮应上传** |

- 用户说「上传改了的 / 上传修改题解」时：扫描范围内所有 `修改_题解.md`，**仅上传没有** `修改_题解.已上传` 的题；已有标记的在对话里一句带过「已上传，跳过」即可。
- **`upload_sol` HTTP 成功后**：在同目录写入空文件（或一行日期）`修改_题解.已上传`。
- **若之后又改写了** `修改_题解.md`（内容相对上次上传有变）：先**删掉**该标记，再上传，成功后重新写入标记。
- 用户**明确说**「重新上传 / 再传一遍」某题时：可忽略标记强制上传，成功后仍保持/写入标记。
- **不要**把「是否已上传」写进 `修改说明.txt` 正文句式里；标记文件单独存在即可。

### 5.5 硬性规则：朴素满 AC → 必须加 hack 测例（不要多想）

适用：**情况二**（或「前半朴素 + 后半正解」）里，题解给出的**朴素/暴力**代码在用 `submit_code_and_get_result.py` 提交后得到**满分 AC**（或几乎满分，无法体现与正解的区分度）。

这表示现有 `data/` 太弱，**禁止**就此收工。必须执行：

1. **分析为何没挂**：常见原因是规模不够、随机数据让最坏复杂度达不到、图/邻接顺序对 DFS 太友好等（对照 P4942 双倍边坏序、P3878 全等序列卡 $O(n^2)$ 扩展）。
2. **在题面约束内构造 hack**：新增 `.in/.out`（编号接在现有测例后），写入 `data/config.yaml`；目标是让**朴素 TLE / 明显不满分**，同时**正解仍 AC**。本地可用计时粗测，最终以 OJ 提交为准。
3. **若题面最大规模下，正确的朴素复杂度对 C++/Java 仍轻松过**（例如题面 $n\le10^4$ 而朴素 $O(n^2)$）：**同步放宽** `题面.md` 中相关范围（如 $n\le10^5$），使「大数据朴素会挂」与题面一致，再造满规模最坏测例；用 `utils/upload_problem.py`（或等价接口）上传更新后的题面。
4. **上传数据**：`utils/upload_testdata.py` 上传整个 `data/`（保持测例与本地一致，不要默削）。
5. **复测**：再交朴素（应不满分/TLE）与正解三语言（应 AC）。题解正文里关于「大数据会超时」的表述若仍写旧规模，一并改掉。
6. **`修改说明.txt` 仍不要写** AC/TLE/造数过程；hack 是维护动作，不是题解叙事。

口诀：**情况二的朴素拿满分 = 数据没就绪，先 hack 再交差。**

## 6. 工作步骤

1. 读 `题面.md`、`题解.md`、`题解生成规范.md`、`题解模板.md`。
2. 抽出当前算法核、数据范围、现有代码风格。
3. 按第 2 节判定：情况一 / 情况二 / 无需优化。
4. 无需优化 → 对话结束（不写文件）。
5. 要优化 → 按第 3 节骨架写 `修改_题解.md`，代码按第 4 节；并写 `修改说明.txt`（原题解是…，因为…，所以改为…）。
6. **按第 5 节三语言在线提交**；WA/RE 修代码，TLE/约半测不过则补正解后再交。
7. **情况二：若朴素在线满分 AC → 按 5.5 加 hack（必要时改题面规模）→ upload_testdata → 复测朴素不满分、正解 AC。**
8. 自检清单：
   - [ ] `修改_题解.md` 读起来是独立题解，无「不必用某某 / 相比原解」类对比句
   - [ ] 若原解是线段树/树状数组等：已强制前补朴素（§2.1.3），未用收益门槛否决
   - [ ] 情况二朴素段第一句已写「正解是…，朴素也能拿一定分」
   - [ ] 已过第 2.0 节收益门槛（算法真降 + 代码量明显变少）
   - [ ] 正文公式中的名字（如 $dp$、$value$）与三语言代码标识符一致
   - [ ] 一二级标题、`### Python/Java/C++`、`$变量$` 与原题解版式一致（情况二则按 §3.2）
   - [ ] 情况二有完整暴力三语言 + 正解三语言（且确实属于「复杂板子」，或第 5 节在线证明必须补正解）
   - [ ] 情况二终态：朴素在线**未**满分 AC；若曾满分，已按 §5.5 hack 并复测
   - [ ] 中文关键注释、朴素 I/O、Java `Main`
   - [ ] 未覆盖 `题解.md`
   - [ ] `修改说明.txt` 符合「原解法 → 原因 → 新解法」句式，无提交流水
   - [ ] 三语言已用 `submit_code_and_get_result.py` 提交；该 AC 的代码已 AC（或已记录失败原因）
   - [ ] 若用户要求上传：只传无 `修改_题解.已上传` 的题；成功后写入该标记；已有标记的不重复传
