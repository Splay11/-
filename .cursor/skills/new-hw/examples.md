# new-hw 判定对照

## 收益门槛（先看）

| 问题 | 答「否」则不要改 |
|------|------------------|
| 算法是否从「难板子」降到「明显更简单」？ | 仅是二分 / 前缀和 / 双指针微调 → 不改 |
| 优化后三语言总代码量是否明显变少？ | 差不多或更长（尤其多出一整段暴力）→ 不改 |
| 新手读完是否少记一个重概念？ | 概念数不减 → 不改 |

口诀：**换了个说法但代码还那么长 = 没必要改。**

**硬性例外：** 原题解是**线段树 / 树状数组**（以及树剖、网络流等同类高级板子）→ **不要套收益门槛来否决**，直接前补朴素 + 后写正解（见 SKILL §2.1.3）。

## 情况一：换成更简单的解

| 原题解 | 何时可降 | `修改_题解.md` |
|--------|----------|----------------|
| 状态压缩 DP + DFS | $n$ 很小，子集本质是「选或不选」，普通 DFS/回溯就能过，且去掉 bit 后代码更短 | 只写 DFS/回溯的**全新题解**（正文勿提状压） |
| 正确 DP + 一堆滚动/花活表述 | 算法核已是本题最好懂的正解，只是优化讲得绕 | **仍写 DP**，去掉多余优化与绕口写法，代码写短；**不要**改成 DFS |
| Dijkstra + 堆 | 边权全 1 的网格/无权图 | BFS |
| 矩阵快速幂 | $n$ 很小，递推直接模拟过 | 循环递推 |

**不要**把「线段树 / 树状数组」放进情况一里纠结能不能换成前缀和——一律情况二前补朴素（除非数据小到裸扫就能全 AC，且你已验证，那时仍建议保留「朴素拿分 + 正解」结构更稳妥；默认仍强制前补）。

反例：

- 原题解是二分答案 + 前缀和，$n\le 10^5$。这已经是简单正确解，**不要**再拆成「暴力枚举高度 + 二分扫一遍」。
- 地宫跳 $1/2/3$ 类：$DP$ 比 DFS 更好懂时，**不要**为「朴素」硬加 DFS 半段。

## 情况二：必须复杂解，但要先暴力

| 原题解 | 动作 | 朴素铺垫 | 正解 |
|--------|------|----------|------|
| **线段树 / 树状数组** | **硬性：必须前补** | 每次询问扫一遍 / 暴力改点 | 线段树或树状数组 |
| 树剖、网络流、主席树等 | **硬性：必须前补** | 对应暴力 | 原板子 |
| 最短路 $n\le 10^5$ | 优先前补 | DFS/枚举路径（说明会爆） | Dijkstra / 0-1 BFS |
| 背包 $n\le 100,\;W\le 10^5$ | 可前补 | 枚举选或不选 | 一维 DP |

**不要**对「排序 / 前缀和 / 二分答案 / 双指针 / 普通 DFS / 简单 DP」走情况二。

暴力段必须三语言都有中文注释；正解段同样。朴素段第一句写清「正解是…，朴素也能拿一定分」。

`修改说明.txt` 句式：原题解的解法是…，因为…（太复杂等），所以新题解修改为…。不写提交结果。

## 无需优化

- 算法已是数据范围下最朴素的正确做法（如排序 + 二分、双指针、一次 DFS、前缀和）。
- `## 解题思路` 已分点，三语言已有关键中文注释，I/O 也不花。
- 优化后代码量 / 概念负担没有明显下降。
- 不要为了交差再写一份几乎相同的 `修改_题解.md`。

## 在线验 AC

写出 `修改_题解.md` 后，用 `utils/submit_code_and_get_result.py` 交三语言：

| 结果 | 动作 |
|------|------|
| WA / RE / 编译错 | 改代码本身，重交 |
| TLE / 大约只过 50%～60% | 在朴素解后补正解（情况二骨架），再交正解至 AC |
| 全 AC | 通过 |

判定阶段以为「简单解能过」但线上过不了 → 升级为暴力 + 正解，正文仍不提旧题解。

## 只改写法（仍出 `修改_题解.md`）

算法不用换，但原题解有下列之一：

- 几乎无中文注释，或只有一种语言有注释；
- Python 用 `sys.stdin.buffer`、Java 快读，新手读起来费劲；
- 思路揉成一大段，没有分点。

按原算法重写，骨架仍用原题解的一二级标题；**不要**借机换成另一套篇幅差不多的算法。写完同样要做第 5 节在线提交。
